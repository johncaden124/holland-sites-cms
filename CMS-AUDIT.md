# CMS audit: `@hollandtech/site-cms` v0.6.0

A review of the content contract, its breaking-change protection and the CLI, against the brief in
four sections. Each check is marked **PASS** (it already held, with the evidence) or **FIXED** (it
did not, and v0.6.0 changes that). The branch is `claude/contract-review-v0.6.0`.

**Summary.**
- The contract now covers the whole business, and every addition is optional.
- There is a generated JSON Schema and a runtime validator that reports every problem at once.
- API and schema drift fails CI unless the version is bumped by the documented rule.
- Both templates are smoke-tested against each change.
- The CLI has `import-content` and `new-site` for the generator.
- 88 → 147 tests.
- Both existing templates and the hub type-check and pass against v0.6.0 unchanged, and parity
  passes against a real local hub seeded with both demo tenants.

How it was verified, besides this repo's own suite:
- **`template-landscaping` @ `a95d5cf` and `template-hvac` @ `c848ae7`**: each had the packed v0.6.0
  installed over its pinned v0.5.0, then ran:
  - `npm test`: 24 and 28 tests pass;
  - `astro check`: 0 errors;
  - `site-cms parity`: PARITY OK against the mock hub, and against the real hub (below).
- **`holland-sites-hub` @ `7d64211`**:
  - `pnpm install`, `pnpm payload migrate`, `pnpm seed:tenant clients/demo-landscaping` and
    `clients/demo-hvac`, then `pnpm dev` on :3000. Each bot key sees exactly its own tenant.
  - `pnpm typecheck` passes with v0.6.0 installed.

### 1.2 Additions optional; v0.6.0; changelog: FIXED
- Every new field and group is optional. v0.5 content still validates (`test/validate.test.ts`,
  "accepts v0.5 content").
- Both templates compile unchanged: `astro check` reports 0 errors.
- The mappers omit a group the hub sends all-null, so v0.5 tenants map exactly as before
  (`test/cms.map.test.ts` › "maps nothing new for a v0.5 tenant").
- `package.json` is `0.6.0`. The `CHANGELOG.md` entry covers the additions, the new validation,
  the CLI, and the one behaviour change (the default media host).

### 1.3 JSON Schema: FIXED
- `schema/site-content.schema.json` is generated by `ts-json-schema-generator` from `types.ts`
  (`npm run schema`, `scripts/build-schema.mjs`) and shipped on the `./schema` subpath.
- The root is `LocalContent`, and every content type is a named definition.
- `Photo` is rewritten to `{src, width, height}` so the schema doesn't depend on Astro
  (`test/validate.test.ts` › "knows nothing of Astro").
- CI runs `npm run check:schema`, which fails if the committed schema is stale.

### 1.4 `validateSiteContent()`: FIXED
- `src/validate.ts`, on the root and on `./validate`. The schema is compiled by Ajv at build time
  into `src/generated/validators.ts`, so there is still no runtime dependency.
- It returns `{ ok, problems: [{ path, message }] }` with every problem at once, with paths like
  `site.site.business.phone.e164` and `services[0].icon`.
- It also checks one thing the schema can't: `copy.businessName === site.name`.
- It never reads a local `ImageMetadata` Proxy (tested with a trapping Proxy).
- **In `createCms()`**:
  - `local` is validated at import;
  - each hub getter validates its mapped result and throws one error listing every mismatch;
  - tested in `test/cms.test.ts`: "checks the local content at import…" and "lists every mismatch in one error".
- **In the CLI**:
  - `export-content --validate`;
  - `import-content` and `new-site` always validate before writing.

## Section 2: breaking-change protection

### 2.1 Type snapshot plus bump rule: FIXED
- API Extractor reports for all 10 typed entry points are committed in `etc/*.api.md`
  (`scripts/api-report.mjs`). `npm run api:check` fails on any drift (CI).
- `scripts/check-version-bump.mjs` runs on PRs and compares `etc/` and `schema/` with the base branch.
- **Rule**:
  - Before 1.0, any change needs at least a minor bump, and a patch bump is refused.
  - From 1.0, additions need a minor bump; removed or altered lines need a major.
  - Documented in README › Release flow.
- Verified both ways against `main`:
  - 0.5.1 → 0.6.0 passes;
  - 0.5.1 → 0.5.2 fails with "needs a minor bump… (pre-1.0: any contract change is a minor)".

### 2.2 Consumer smoke test: FIXED (needs a secret; see decisions)
- `.github/workflows/consumer-smoke.yml` does the following for each template in `consumers.json`
  (landscaping and HVAC, each pinned by SHA because neither repo has tags):
  1. checks it out at the pinned ref;
  2. `npm pack`s this commit and installs it over the template's own version;
  3. runs `npm test`, then `npm run parity` against `scripts/mock-hub.mjs`.
- The mock hub serves the template's own captured fixtures, and its media, on `:3000`, so no hub
  secret is needed.
- The templates are **private**, so the workflow needs a `CONSUMERS_TOKEN` repository secret: a
  fine-grained PAT with read-only Contents on both template repos. Until it is set, the job fails
  with an explicit error saying so. Setup is documented in the README.
- The exact steps were run locally for both templates, and all passed.

### 2.3 Retry, cache, one-tenant and media-host tests: PASS
Each already had a test that fails if the behaviour breaks:

| Behaviour | Test (`test/cms.test.ts`) |
| --- | --- |
| A response with two tenant ids throws | "refuses a list whose documents come from two tenants, naming both"; also "catches a tenant that changes between collections" |
| A media URL on a non-allowed host throws | "rejects a photo on any other host, naming the field" (+ 5 origin variants) |
| A 5xx retries once, then throws with the URL | "reports a persistent 5xx with its status text and URL" (asserts 2 calls and the URL); "retries a 5xx once and then succeeds" |
| A 4xx does not retry | "names the URL, Payload message and the API-key fix on a 401, without retrying" (asserts 1 call). **Added** "does not retry any 4xx, not only an auth failure" (404), so the claim isn't carried by the 401 branch alone |
| Cache | "keeps one fetch per collection for a whole build", "evicts a failed fetch…", "gives two createCms instances their own caches…", "refetches after a second in dev…" |

### 2.4 Error messages name the field, the URL and the fix: FIXED
- **Before**:
  - fetch errors already named all three (PASS);
  - the missing-field error named the field and the fix but **not the URL**;
  - the media-origin error named the field and the media URL but **no fix and not the hub URL**.
- **Now**: both name the hub collection URL they came from, and a fix. The tests assert the whole
  message text:
  - "fails the build and names the path, rather than shipping a blank";
  - "names the field, the media URL, the hub URL it came from and the fix";
  - "checks the local content at import…".

## Section 3: the CLI

### 3.1 `export-content`: FIXED
- **Before**: it wrote only `content.json` (`--out`) and `media/` (`--media`). The hub's
  `seed:tenant` also needs `tenant.json`, which had to be written by hand.
- **Now**: `--client <slug> [--dir clients]` writes `clients/<slug>/tenant.json`, `content.json`
  and `media/`.
  - The tenant fields come from the content and the repo's package name, an existing
    `tenant.json` is merged, and flags override.
  - The hub's `tenant.json` rules are checked (kebab-case slug, name, plan and niche enums).
- **Evidence**: run in template-landscaping, the `content.json` was byte-identical to the hub's
  `clients/demo-landscaping/content.json`, with the same 23-file media list. template-hvac's export
  equals the hub's `clients/demo-hvac/content.json`.
- **`--validate`**: FIXED. It runs `validateSiteContent` plus the hub's structural rules on the
  output before anything is written.

### 3.2 `import-content <file>`: FIXED
- It writes the ten `src/data/*.ts` modules in one canonical format and places the media.
- **Round trip** (`test/roundtrip.test.ts`, run through the real CLI and Vite): starting from the
  hub's demo `content.json`, import → export gives the same file **byte for byte**, and import →
  export → import gives **byte-identical `src/data`**.
- Per your decision the generator owns the format: a hand-written template's comments and import
  names are not reproduced, but its content is.

### 3.3 `new-site`: FIXED
`new-site --from <content.json> --template <name> --out <dir>`:
1. clones the template at its `consumers.json` pin (or `--ref`) and drops the history;
2. imports the content and media;
3. sets `CMS_REQUIRED` (true unless `--no-cms-required`);
4. sets `PAYLOAD_URL`, `PUBLIC_MEDIA_HOST` and `PUBLIC_SITE_URL` in the template's `.env.example`,
   keeping its other variables.

It cleans up after itself on failure. It is tested against a local git repo (`test/newSite.test.ts`)
and was run for real against GitHub:
- `new-site … --template template-landscaping --out acme` produced a tree that passes `astro check`
  (0 errors) and the template's 24 tests, and builds in CMS mode.
- The same tree's standalone build fails with the `CMS_REQUIRED` error, as intended.

### 3.4 `parity` and `capture-fixtures` against the hub demo tenants: PASS
- Against the real local hub (`pnpm dev`, both demos seeded):
  - `capture-fixtures` captured all 7 collections for each tenant;
  - `parity` reported PARITY OK for landscaping (`leapfly-demo`) and HVAC (`demo-hvac`).
- The environment each command needs is now in its `--help` and in a README table:
  - **`parity`**: `PAYLOAD_URL`, `PAYLOAD_API_KEY` (`pnpm bot-key <slug>` in the hub) and
    `PUBLIC_SITE_URL`, with one value for both builds.
  - **`capture-fixtures`**: `PAYLOAD_URL` and `PAYLOAD_API_KEY`.

### 3.5 `--help`, non-zero exit, and only the error on failure: FIXED
- **Before**:
  - there was no per-command `--help`;
  - `parity` streamed both builds' logs, even on failure;
  - `capture-fixtures` printed progress, then failed halfway with partial files written;
  - `export-content` printed its problems via `console.error` and `process.exit`;
  - bare `site-cms` printed its usage to stdout.
- **Now**, for all five commands:
  - `--help` exits 0;
  - a failure exits 1 with empty stdout and only the error on stderr (`parity` puts the build
    log's last 40 lines inside the error);
  - `capture-fixtures` writes nothing unless all 7 collections succeed.
- `test/cli.test.ts` asserts all of this, with 20 cases.

## Needs your decision

1. **The hub schema doesn't have the v0.6 fields yet.** The hub's `site`, `services` and
   `testimonials` collections need `business`, `copy`, `flags`, `priceHint`, `rating`, `date` and
   `source`, plus a migration, before any tenant can set them. The mappers are ready and expect
   Payload's shapes: `{ text }` rows for `serviceAreaTowns`, a `hasMany` select for `dayOfWeek`,
   and a date field for `date`. That is a hub PR; I didn't open it.
2. **`CONSUMERS_TOKEN` secret.** Create a fine-grained PAT (read-only Contents on template-landscaping
   and template-hvac) and add it as a repository secret. Until then the smoke workflow fails with an
   explicit error.
3. **Stricter `createCms` at import.** `local` is now validated, and the schema rejects unknown
   keys. Both templates pass. A future template with an extra key in `src/data` will fail at
   import, naming the key. That is intended, but it is a behaviour change worth knowing about.
4. **Doc-only changes count as contract changes.** API Extractor reports mark undocumented members,
   so adding a doc comment to an exported type changes `etc/` and, pre-1.0, needs a minor bump.
   The alternative is to strip those markers from the comparison.
5. **`Social['label']`.** It is still `x | linkedin | facebook | instagram`. Home-service clients
   often need `google`, `yelp`, `nextdoor`, `youtube` or `tiktok`. Widening the union is a
   type-level change for any template that switches over it exhaustively, so I left it for you.
6. **`new-site` output isn't a git repo.** It removes the template's history and stops there. Should
   it `git init` and make a first commit, or leave that to the generator?
7. **Stale media-host references elsewhere.**
   - template-landscaping's and template-hvac's `.env.example` still say
     `PUBLIC_MEDIA_HOST=media.hollandtech.com`.
   - The hub README's remote-seed section says `MEDIA_PUBLIC_URL=https://media.hollandtech.com`,
     while its `wrangler.jsonc` says `media.hollandsites.com`.
   
   `new-site` already writes the right value into client repos.
8. **One copy of the trade list.** The hub could import `TRADES` from
   `@hollandtech/site-cms/trades` instead of keeping `NICHES`, so the two lists can't drift. Today
   they are equal by hand.
